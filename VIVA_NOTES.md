# Yall Compiler — Viva Voce Notes & Examination Guide

This document contains likely viva voce questions and short, precise, technically accurate answers based directly on the implementation of the **Yall** compiler.

---

## General & Architecture

### Q1: What are the phases of the Yall compiler pipeline?
**Answer**:
The Yall compiler executes in 7 sequential stages:
1. **Lexical Analysis (Lexer)**: Converts source text into tokens.
2. **Syntax Analysis (Parser)**: Builds the Abstract Syntax Tree (AST).
3. **Semantic Analysis**: Type checking, symbol resolution, and scoping.
4. **Intermediate Representation (IR)**: Generates linear Three-Address Code (TAC).
5. **Optimization**: Optimizes TAC via constant folding, propagation, and dead code elimination.
6. **Code Generation**: Emits stack-machine bytecode.
7. **Virtual Machine (VM)**: Executes bytecode using a heap-based frame stack.
If any phase detects an error, the compiler stops immediately without running later phases.

---

## Phase 1 & 2: Lexing and Parsing

### Q2: Why use a Recursive-Descent Parser instead of a table-driven parser (e.g. Yacc/Bison)?
**Answer**:
1. **Clarity and Debuggability**: Each grammar non-terminal directly corresponds to a C++ member function (e.g., `parseStatement()`, `parseExpression()`). This allows easy inspection with ordinary debuggers.
2. **Superior Error Messages**: Recursive descent makes contextual error reporting natural and flexible because the parser knows the exact construct it is attempting to match.
3. **No External Generator Dependencies**: Written in 100% standard C++17 with zero external tools or runtime tables.

### Q3: What is panic-mode error recovery and how is it implemented?
**Answer**:
Panic-mode recovery is an error-recovery strategy where the parser, upon encountering an unexpected token, emits a syntax error and synchronizes by advancing tokens until it reaches a known statement boundary (a synchronizing token like `;` or a keyword like `func`, `if`, `till`, `rep`, `let`, `fixed`). This prevents cascading syntax errors while allowing the parser to find multiple syntax errors in a single pass.

## Phase 3: Semantic Analysis

### Q4: How does `let` infer its type?
**Answer**:
In `SemanticAnalyzer::analyzeVarDecl()`:
1. When encountering `let x = expr;`, the analyzer analyzes the initializer expression `expr` and computes its evaluated type (`expr->type`).
2. If `expr->type` is `Type::NOTHING` (e.g. calling a void function), the compiler reports an error: `"cannot infer a type from a call to a function that returns nothing"`.
3. Otherwise, `vd->resolvedType = expr->type`, and variable `x` is registered in the scoped symbol table with this inferred type.

### Q5: How are scoped symbols and shadowing managed with `uniqueName`?
**Answer**:
A stack of scopes (`Scope`) is maintained. Variable lookups search from the innermost active scope up to the global scope. Shadowing in an inner block is legal. To eliminate ambiguity for downstream IR generation, every declared variable receives a globally unique name (`x`, `x_2`, `x_3`, etc.) generated by a per-name counter, which is attached to all `VariableExpr` and `VarDecl` AST nodes.

## Phase 4: Intermediate Code Generation (TAC)

### Q6: Why do logical operators `&&` and `||` require jumps in Three-Address Code?
**Answer**:
In Yall, `&&` and `||` enforce **short-circuit evaluation semantics**:
- For `a && b`: If `a` evaluates to `no`, `b` must **never** be evaluated (especially important if `b` contains a function call with side effects or an error).
- Therefore, TAC emits:
  ```text
  t = a
  IF_FALSE t GOTO Lend
  t = b
  Lend:
  ```
- Similarly, `a || b` uses `IF_TRUE t GOTO Lend`. Evaluating both operands unconditionally would violate language semantics.

### Q7: How does explicit widening work in TAC?
**Answer**:
Yall enforces implicit widening only from `num -> decimal`. In TAC, this is represented by an explicit `I2D` instruction into a fresh temporary. This occurs whenever an integer is assigned to a decimal variable, passed to a decimal parameter, returned from a decimal function, or mixed with a decimal operand in arithmetic or comparisons.

## Phase 5: TAC Optimization

### Q8: What is constant folding, and why is `DIV` by a variable never removed or folded?
**Answer**:
- **Constant Folding**: The compile-time evaluation of operations whose operands are known constants (e.g. `2 + 3 * 4` becomes `14`).
- **Why `DIV` by a variable is never removed**: In Yall, division by zero is a **mandatory runtime error** (exit code 3). If `10 / z` were folded or deleted as dead code when `z` is unused, a division-by-zero runtime trap would be silently suppressed, changing the observable program behavior. Only divisions with a **guaranteed non-zero constant divisor** may be folded or eliminated.

### Q9: Why must temporaries not be assumed to be single-assignment?
**Answer**:
Because short-circuit `&&` and `||` assign the same temporary in two branches: once before the jump and once after the jump (e.g. `t = a; IF_FALSE t GOTO Lend; t = b; Lend:`). If an optimization pass assumed single static assignment (SSA) without counting definitions, it would incorrectly forward or overwrite `t`, corrupting program logic.

## Phase 6 & 7: Bytecode & Virtual Machine

### Q10: Why choose a Stack Machine architecture for the bytecode?
**Answer**:
1. **Compact Instructions**: Stack instructions (like `ADD_I`, `RET_VAL`, `POP`) implicitly operate on the top of the stack and require no explicit register operands, yielding small bytecode sizes.
2. **Simple, Clean Translation**: Expression trees in TAC translate directly to Postfix/Reverse Polish Notation on the stack: evaluate arguments, emit operation, store destination.
3. **VM Portability**: A stack machine requires only a simple array for the operand stack and an array of frames for local variables, avoiding complex register allocation algorithms.

### Q11: How does recursion work in the Virtual Machine without C++ stack overflow?
**Answer**:
The VM maintains its own call stack (`std::vector<Frame> callStack_`) allocated on the **heap**, rather than using C++ function recursion.
- When `CALL` executes, the VM pushes a new `Frame` object containing local variable slots and a program counter (`pc`), popping arguments into slot indices `0` through `numParams - 1`.
- Deep recursion increases the vector size on the heap up to a configured safety limit (`MAX_CALL_DEPTH = 100,000`). If exceeded, it safely raises a `Runtime error: stack overflow (recursion too deep)` and exits with code 3, preventing the host C++ process from crashing with a segmentation fault.

### Q12: How is floating-point output handled in the VM?
**Answer**:
Yall follows Python-like shortest round-trip double formatting:
- It attempts precisions `1` through `17` with `snprintf(buf, "%.*g", p, d)` and validates that `strtod` parses the exact original double back.
- If the double has no fractional component (e.g. `3.0` or `100.0`), it guarantees an explicit `".0"` suffix so that floats are never ambiguous with integers.
- Special values `nan`, `inf`, and `-inf` are printed as exact text tokens.
